# Architecture Decision Records — Easy Transfer Frontend

## 철학
해커톤 MVP. 서울역 1개 역, 선형 플로우만 동작하면 된다. 외부 의존성은 화면 구현에 필요한 최소한(네비게이션, SVG)만 추가하고, 백엔드가 아직 불안정할 수 있으므로 목데이터로 먼저 완성한 뒤 실제 API로 교체 가능한 얇은 경계를 둔다.

---

### ADR-001: Expo(React Native) + TypeScript
**결정**: `frontend/`는 Expo 관리형 워크플로우 기반 React Native + TypeScript 앱으로 만든다.
**이유**: 사용자가 "앱개발"(네이티브 앱)을 명시적으로 요청했다. Expo는 iOS/Android를 단일 코드베이스로 다루고, Expo Go로 별도 빌드 없이 즉시 기기에서 시연할 수 있어 해커톤 시연에 유리하다.
**트레이드오프**: 완전한 네이티브 모듈이 필요해지면 bare workflow로 eject해야 할 수 있다. 이번 MVP(지도 이미지 + SVG 오버레이 + 화면 전환)는 Expo 관리형 워크플로우로 충분하다.

### ADR-002: React Navigation (native-stack)으로 선형 플로우 구성
**결정**: OriginInput → DestinationInput → Loading → Guide → Arrived 화면을 `@react-navigation/native-stack` 하나로 연결한다. 전역 상태 라이브러리는 쓰지 않는다.
**이유**: 플로우가 선형이고 분기가 없다. route params로 화면 간 필요한 값(입력 텍스트, profile, RouteResponse)만 넘기면 충분하며, 네이티브 전환 애니메이션·back 제스처를 공짜로 얻는다.
**트레이드오프**: 나중에 플로우가 비선형이 되거나 여러 화면에서 같은 상태를 동시에 구독해야 하면 상태 관리 라이브러리 도입을 재검토해야 한다. 화면 구성 자체는 한 번 바뀐 적이 있다(목적지 픽리스트 2화면 → 자유 입력 2화면 + 로딩 1화면) — route params 기반 설계 덕분에 화면을 추가/교체해도 이후 화면들의 인터페이스(`{ route: RouteResponse }`)는 그대로였다.

### ADR-003: ~~지도는 원본 이미지 1장 + 클라이언트 카메라 팬~~ (ADR-014로 대체됨)
**결정(당시)**: 역이용안내도 원본 이미지 1장을 번들에 넣고, 프론트가 직접 관리하는 노드→픽셀좌표 테이블(`src/data/nodeCoordinates.ts`)로 스텝마다 SVG 오버레이와 카메라 팬/줌을 계산한다.
**대체 사유**: v1.2 백엔드가 노드마다 정규화 좌표(`imageX`/`imageY`)를 직접 내려주면서 프론트가 좌표를 관리할 이유가 사라졌다. 좌표 테이블과 카메라 계산 로직은 삭제했다. → `ADR-014`

### ADR-004: 목데이터(contracts/v1.2 fixture) 우선, 실제 API는 서비스 계층 뒤에 숨김
**결정**: `src/data/fixtures/`에 `contracts/v1.2`의 고정 JSON을 그대로 복사해 두고, `src/data/routeService.ts`가 이 fixture를 반환하도록 먼저 구현한다. 실제 백엔드(`GET /api/v1/maps/{mapId}/places`, `POST /api/v1/routes`) 연동은 같은 함수 시그니처를 유지한 채 내부 구현만 fetch로 바꾼다.
**이유**: 해커톤 중 백엔드 가용성이 불확실해도 프론트 화면 작업이 막히지 않는다. 계약(contract)이 이미 얼어있으므로(frozen fixtures) fixture와 실제 응답의 shape가 동일해 교체 리스크가 낮다.
**트레이드오프**: fixture가 실제 배포된 API 응답과 미묘하게 달라질 경우(필드 누락 등) 늦게 발견될 수 있다 — 연동 시점에 반드시 실제 응답으로 스모크 테스트한다.

### ADR-005: MVP UI 언어는 영어 단일, 다국어 전환 없음
**결정**: 화면의 모든 텍스트는 영문으로 고정한다. 한/영/일/중 언어 전환 UI는 만들지 않는다.
**이유**: 이번에 확정한 디자인 기준 목업(`Easy Transfer App.dc.html`)이 이미 영문 단일 UI로 만들어져 있고, 기획안의 핵심 사용자 정의("한국어 소통이 어려운 외국인 관광객")와도 부합한다. 다국어 전환은 별도 데스크톱 스펙 문서(`Frontend Spec.dc.html`)에만 존재하며, 이번 모바일 MVP의 확정 범위가 아니다.
**트레이드오프**: 한국어를 선호하는 사용자나 일본어/중국어권 사용자를 위한 대응은 이번 범위에서 제외된다. 필요해지면 별도 스코프로 i18n 사전을 추가한다.

### ADR-006: react-native-svg로 경로 오버레이 구현
**결정**: 경로 선, 화살촉, 현위치 펄스 마커는 `react-native-svg`의 `Svg`/`Path`/`Circle`로 그린다.
**이유**: 디자인 핸드오프의 웹 목업이 이미 동일한 SVG 구조(외곽선+본선+대시 애니메이션+펄스 원)로 정의되어 있어 1:1로 옮길 수 있다. RN 생태계에서 SVG 경로/애니메이션을 다루는 표준 라이브러리이기도 하다.
**트레이드오프**: 대시 흐름 애니메이션(`stroke-dashoffset`)과 펄스는 `Animated` API로 직접 구현해야 한다(웹의 CSS `@keyframes`를 그대로 쓸 수 없음).

### ADR-007: 에러를 종류별로 구분해서 표시한다 (일반 Error 금지)
**결정**: `routeService.ts`는 `Error` 대신 `RouteServiceError`(kind: `NETWORK`|`NOT_FOUND`|`INVALID_REQUEST`|`SERVER_ERROR`)만 던진다. 화면은 `kind`별로 다른 문구·버튼을 보여주는 공용 `ErrorState` 컴포넌트로 렌더링한다.
**이유**: 길 안내 도구에서 "안 될 때"의 신뢰가 제품의 전부다. "오프라인입니다"와 "이 경로는 존재하지 않습니다"를 같은 문구로 뭉뚱그리면 사용자가 뭘 해야 할지 알 수 없다(연결을 확인해야 하는지, 목적지를 바꿔야 하는지). 자세한 시나리오는 `docs/PRD.md` "데이터 로딩 실패" 표 참조.
**트레이드오프**: 백엔드가 이 4종 분류와 다른 에러 체계(예: 커스텀 에러 코드)를 쓰면 `routeService.ts`의 매핑 로직을 다시 맞춰야 한다.

### ADR-008: ~~좌표 미스는 명시적 "지도 표시 불가" 상태로 보여준다~~ (ADR-014로 대체됨)
**결정(당시)**: 프론트 좌표 테이블에서 노드를 못 찾으면 임의의 fallback 좌표 대신 `null`을 반환하고, 지도를 회색 placeholder로 대체한다.
**대체 사유**: 좌표가 경로 응답에 함께 오므로 "테이블에 없는 노드"라는 상태 자체가 사라졌다. 다만 그 근거였던 원칙 — **틀린 위치를 그럴듯하게 그리느니 안 그린다** — 는 유효하며, 아직 이미지가 없는 지도와 현장 검증 전인 demo 좌표에 그대로 적용된다(`ADR-016`).

### ADR-009: 항목 0개 경로는 안내 화면 진입 즉시 감지해 도착 화면으로 대체한다
**결정**: 세그먼트를 펼친 체크리스트 항목이 0개인 응답(출발지=도착지 등)은 유효한 응답으로 취급한다. `GuideScreen`이 마운트 시 이 조건을 확인해 `navigation.replace('Arrived', { route })`로 즉시 대체한다.
**이유**: 빈 배열의 첫 원소에 접근하면 그 자리에서 크래시한다 — 실제로 초기 구현에 있던 버그였다. v1.2는 이 경우를 "200 + summary 0 + 노드 하나짜리 MAP 세그먼트"로 내려주므로(`route-enums-v1.2.md`) 응답이 비어 있는 게 아니라 **펼친 결과가** 비어 있다 — 가드는 세그먼트 개수가 아니라 체크리스트 항목 개수를 봐야 한다.
**트레이드오프**: 관문이 이 화면 하나뿐이라, 앞에 새로운 중간 화면이 생기면 거기에도 같은 가드가 필요하다는 걸 잊기 쉽다 — 화면을 추가할 때마다 이 ADR을 다시 확인한다.

### ADR-010: 안내 중 이탈은 두 번째 항목부터 확인을 받는다
**결정**: `GuideScreen`에서 하드웨어 back/스와이프 제스처를 `beforeRemove` 이벤트로 가로채, 체크한 항목이 하나라도 있을 때만 "Leave this guide?" 확인 다이얼로그를 띄운다. 첫 스텝에서는 확인 없이 나간다.
**이유**: 첫 스텝은 아직 "안내를 시작했다"고 보기 어렵고(둘러보다 실수로 진입했을 수 있음), 확인 다이얼로그를 매번 띄우면 오히려 짜증나는 마찰이 된다. 반면 두 번째 스텝 이후는 실제로 걷고 있는 사용자일 가능성이 높아, 실수로 스와이프해 진행 상황을 잃는 것을 막을 가치가 크다.
**트레이드오프**: "몇 번째 스텝부터"라는 기준 자체가 다소 임의적이다. 사용자 테스트에서 마찰이 크면 기준을 조정한다.

### ADR-011: 도착 후에는 안내 화면을 스택에서 완전히 제거한다
**결정**: `ArrivedScreen`의 "Plan another transfer"는 `navigation.popToTop()` 대신 `navigation.reset({ index: 0, routes: [{ name: 'OriginInput' }] })`을 쓴다.
**이유**: `popToTop()`은 스택의 첫 화면까지 "돌아가는" 동작이라 첫 화면이 여전히 `OriginInput`이면 결과는 같지만, 의미상 "이 안내는 끝났다"를 명확히 하는 쪽은 `reset`이다. 향후 스택 depth가 바뀌거나 초기 화면이 달라져도 안전하다.
**트레이드오프**: 없음 — 동작은 현재 스택 구조에서 `popToTop()`과 동일하지만 의도가 코드에 드러난다.

### ADR-012: 도착지는 픽리스트 대신 자유 텍스트 + 클라이언트 매칭으로 받는다
**결정**: 도착지 화면은 알려진 장소를 나열해 고르게 하지 않고, 자유 텍스트 입력 하나만 받는다. 이후 `Loading` 화면에서 `resolveDestination()`이 `contracts/v1.2` 장소 목록과 대소문자 무시 부분 문자열 일치로 매칭한다. 매칭 실패는 `RouteServiceError('NOT_FOUND')`로 처리해 기존 에러 UX를 그대로 재사용한다.
**이유**: 실제 사용자는 역무원에게 길을 묻듯 "AREX 플랫폼 어디예요?"라고 타이핑하거나 메모해온 목적지를 붙여넣는 쪽에 더 가깝다. 목록에서 정확한 항목을 찾아 스크롤하는 것보다 자연스러운 입력 방식이며, 향후 장소가 많아져도 확장성이 있다(v1.2에서 목적지가 4곳으로 늘었다).
**트레이드오프**: 단순 부분 문자열 매칭이라 오타·다른 표현(동의어, 줄임말)에 취약하다 — "아렉스"처럼 한글 표기나 오타가 오면 실제로는 유효한 목적지인데도 `NOT_FOUND`가 뜬다. MVP는 이를 감수하고, 필요해지면 퍼지 매칭이나 자동완성 제안을 추가한다(`docs/PRD.md` "MVP 제외 사항").

### ADR-013: 출발지 자유 입력은 표시용 레이블일 뿐, 실제 라우팅 출발 노드는 고정이다
**결정**: `OriginInput` 화면에서 받은 텍스트(+ 출구 번호)는 검증하거나 매칭하지 않는다. `originQuery`/`originExitNumber`를 조합해 `originLabel` 문자열만 만들고, 실제 `POST /api/v1/routes` 요청의 `startPlaceId`는 항상 `FIXED_START_PLACE_ID`를 쓴다.
**이유**: Phase 0 백엔드(`contracts/v1.2`)는 `SEOUL_KTX_ARRIVAL` 단 하나의 시작 지점만 지원한다 — 출발지를 매칭 대상으로 삼아봐야 선택지가 하나뿐이라 사용자 입력을 검증할 실익이 없다. 그럼에도 출구 번호를 직접 입력받는 화면을 두는 이유는, 기획안(`기획안_서울역_실내길찾기.md`)이 애초에 "출발지 = 지하철역 입구 기준"으로 정의했고, 사용자가 자신의 실제 위치를 표현할 수 있게 해 안내 문구("Seoul Station · Exit 2")가 사용자 맥락에 맞게 보이도록 하기 위함이다.
**트레이드오프**: 사용자가 서울역이 아닌 다른 역 이름을 입력해도 경로 탐색 결과는 달라지지 않는다 — 자칫 "내가 입력한 출발지가 무시됐나?"라는 오해를 살 수 있다. 백엔드가 여러 출발 지점을 지원하게 되면 이 ADR을 재검토하고 실제 매칭 로직을 추가한다.

### ADR-014: contracts v1.2로 이전 — 좌표는 백엔드가 내려주고, 지도 이미지는 아직 없다
**결정**: 프론트 데이터 계층을 v1.1에서 v1.2로 옮긴다. 응답 모델이 평평한 `steps[]`에서 `segments[]`(`MAP` | `TRANSITION`)로 바뀌었고, 지시문·거리·이동수단은 세그먼트의 `edges[]`가 들고 있다. 좌표는 노드·엣지에 정규화 값(`imageX`/`imageY`, `geometry`)으로 함께 오므로 프론트의 좌표 테이블(`nodeCoordinates.ts`)과 카메라 계산(`useMapCamera.ts`)은 삭제한다. 에러는 응답 본문의 이름 있는 코드(`ROUTE_NOT_FOUND`, `INVALID_PLACE` 등)를 먼저 보고, 없을 때만 HTTP 상태로 떨어진다.
**이유**: 백엔드가 실제로 구현되어(`RouteController`, `JsonGraphRepository`, `graph/seoul-station/map-v1.json`) v1.2를 서빙한다. 좌표를 손으로 관리하던 이유가 "백엔드가 안 준다"였는데 이제 주므로, 그 테이블은 유지할수록 틀려질 부채일 뿐이다.
**트레이드오프**: v1.2는 `direction`(좌/우/직진)과 `landmark`를 없앴으므로, 회전 화살표와 랜드마크 콜아웃은 각각 이동수단 아이콘과 도착 노드 `description`으로 대체했다. 지도 이미지는 둘 중 하나(`seoul-ktx-overview`)만 확보된 상태다 — `ADR-016` 참조.

### ADR-015: 안내 화면은 턴바이턴이 아니라 체크리스트다
**결정**: 경로를 한 스텝씩 교체해 보여주는 대신, 전체 경로를 세로 목록으로 펼쳐 둔다. 완료한 항목은 체크되어 접히고, 현재 항목 하나만 카드로 펼쳐져 지도·설명·"Done — I'm here" 버튼을 갖고, 남은 항목은 번호만 단 채 접혀 있다. 세그먼트는 `toGuideSteps()`가 항목 목록으로 펼친다(엣지 하나 = 항목 하나, 맵 전환 = 항목 하나).
**이유**: 실내에는 측위가 없다 — 앱은 사용자가 어디 있는지 **모른다**. 턴바이턴 UI는 시스템이 위치를 안다는 암묵적 약속을 하는데, 이 앱은 그 약속을 지킬 수 없다. 체크리스트는 진행의 주도권을 사용자에게 넘기고(내가 도착했을 때 내가 체크한다), 헷갈릴 때 앞뒤 항목을 즉시 확인할 수 있게 해준다 — 길을 잃은 순간에 가장 필요한 능력이다. 사용자가 5개 시안 중 이 방향을 선택했다.
**트레이드오프**: 지배적인 요소가 없어 걸으면서 흘깃 보기에는 큰 화살표 방식(시안 B)보다 느리다. 현재 항목 카드를 화면에서 확실히 두드러지게 하고(2px primary 보더, 유일하게 펼쳐진 카드) 항목이 바뀔 때 자동 스크롤로 보정한다.

### ADR-016: 지도 이미지는 에셋 레지스트리로 붙이고, 파일의 실제 크기를 신뢰한다
**결정**: `mapImages[].assetKey` → 번들 이미지 매핑을 `src/assets/mapImages.ts` 한 곳에 둔다. 등록된 키는 `MapPane`이 SVG 좌표계(x `0..mapAspect`, y `0..1`)에 정확히 얹어 배경으로 그리고, 없는 키는 배경 없이 경로만 그린다. 가로세로비는 **계약이 선언한 `intrinsicWidth/Height`가 아니라 번들된 파일의 실제 크기**에서 계산한다.
**이유**: 정규화 좌표는 이미지 전체를 0~1로 덮으므로, 이미지를 `x: 0..mapAspect, y: 0..1`에 놓기만 하면 경로와 지도가 같은 공간을 공유한다 — 뷰박스 확대도 둘에 똑같이 적용되어 별도 정렬 로직이 필요 없다. 실제 크기를 쓰는 이유는 단순하다: 받은 `seoul-ktx-overview.png`는 **2646×1340**인데 계약은 **2657×1786**이라고 선언한다. 선언값을 믿으면 그림이 세로로 늘어나 눈에 띄게 찌그러진다.
**트레이드오프**: 두 가지가 미해결로 남는다. (1) `seoul-arex-exploded`(공항철도 층별 도면)는 아직 없어서 환승 이후 항목들은 배경 없이 경로만 나온다. (2) 계약의 좌표는 스스로 demo 데이터라고 밝히고 있고, 실제로 이 이미지 위에서 검증해 보면 대략 맞는 영역에 떨어지되 실제 지형지물에 핀으로 꽂혀 있지는 않다(예: "ticket gates" 노드가 공항철도 환승 통로 쪽에 찍힌다). 현장 검증 전까지 지도는 "이 구간이 대략 어디쯤"까지만 신뢰할 수 있으며, 안내의 근거는 여전히 텍스트 지시문이다. 선언 크기 불일치는 백엔드에 알려 맞춰야 한다.
